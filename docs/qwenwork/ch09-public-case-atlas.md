# 公开案例图谱：按证据门发布

## 白话导读

这一章帮你搞懂：当别人说「我们有 AI 落地案例」时，你该怎么判断这句话能不能信。你做汇报或选型时，常会遇到一堆看起来很具体的客户名称和场景图谱，但你若直接拿去当证据，可能踩坑——名字漂亮不等于来源能逐条复核。本章给你一道「证据门」：只有拿到案例级外部记录 ID、稳定来源定位和公开许可，才算通过发布门、进公开成员清单。你读完就知道，为什么截至核验日通过门的公开案例是 0；你也能照着补证流程，把一条待核验线索变成真正能引用的案例。你以后引用案例少犯错、好追责。

白话解释：你打开这些案例时，把它们当「别人怎么做的参考」，别当「已经验证过的证据」。你若要对外引用，必须过本章的发布门；在过门前，它们只是线索，不是成员。

## 怎么读案例

先看案例原来的麻烦，再看最后得到的产物；接着核对输入、复用步骤和验收条件，最后再看客户陈述、待核验项和权限边界。具名案例中的结果是客户材料中的陈述，32 个场景图谱是待核验公开场景线索，二者都不能替代你自己的基线和人工判断。

白话解释：你读案例的顺序很关键——先看问题，再看产物，最后才看客户怎么夸自己。你若先看客户陈述，容易被「效果好」带偏；先核对输入和验收条件，你才能判断这案例放不放得进自己的场景。

## 如何复用

1. 用自己的数据、规则、素材、权限和验收口径替换案例输入，不直接复制示例内容。
2. 先做低风险草稿或只读分析，记录人工修改、异常和返工，再决定是否扩大范围。
3. 客户材料中的结果不能直接照搬；产品、品牌、HR、财务或其他业务负责人应按场景人工确认最终结论和对外动作。

白话解释：你复用案例时，换的是你自己的数据、规则和验收口，不是把别人的产物复制过来。你先做低风险草稿试水，记录人工改了什么、返工了多少，再决定要不要扩大；客户说「省了多少」，你不能直接当成你这边的结论。

<span id="claim-public-demo-boundary-01" data-claim-id="claim-public-demo-boundary-01"></span>本书主张：示例产物只证明产物形态，不能证明案例归属、实施成本、生产稳定性或业务效果。

`qwenwork.host` 与 GitHub Pages 链接可以帮助读者观察网页、看板或报告的呈现方式，但不能替代原始案例记录。即使示例仍可访问，也不能据此推断它属于某个候选条目，或已经在生产环境稳定运行。

白话解释：你看到一个能跑的示例页面，只能说明「产物长这样」，说明不了「谁家的、花了多少成本、线上稳不稳」。你哪怕随时能打开它，也不能反推它属于某条候选案例，更不能当作生产环境已经在用。

## 为什么重要

案例名称看起来具体，不等于来源可以逐条复核。R11 的访客页能展示候选名称和标签，但只暴露集合级的 `sheetId=hERWDMS`、`viewId=HdnvUtk` 以及集合级 Wiki 定位；卡片点击后 URL 不变，访客也不能通过「源数据」获得案例级记录 ID、卡片深链或稳定 URL。

这一区别决定了案例能否被引用、纠错和长期维护。若读者无法从正文回到某条原始记录，就无法确认名称与标签是否属于同一条记录，也无法判断链接失效、内容更新或归属变化。因此，集合级可见性只能产生待核验线索，不能直接形成公开案例成员。

白话解释：你如果没法从正文点回原始记录，就分不清「这个名字和那个标签是不是同一条」，更发现不了链接失效或归属变了。你引用案例前必须能逐条回到源头，否则错了也改不了、追不到。

## 发布门与核验方法

公开案例采用逐条发布门，不按集合页可见数量计算：

| 发布门 | 通过条件 | 未通过时的处理 |
|---|---|---|
| 案例身份 | 有案例级外部记录 ID，且不使用本书自建 ID 冒充外部 ID | 保持 pending |
| 来源定位 | 有案例级稳定深链，或在许可范围内保存公开快照及内容哈希 | 不进入公开计数 |
| 内容对应 | 名称、标签、来源定位和示例产物能够稳定对应到同一条记录 | 记录冲突并继续补证 |
| 发布边界 | 不包含未经许可的身份、客户结果或敏感信息 | 去标识化或停止发布 |
| 复核记录 | 保存核验日期、状态、局限和责任角色 | 不创建代表案例卡 |

结构化口径以 [案例来源映射](/qwenwork/appendix-case-source-map) 为准：只有 `included_in_public_count` 为 `true` 的条目才进入公开数量和成员清单。证据卡、来源优先级与冲突处理沿用 [研究与证据链](/qwenwork/ch08-research-evidence-chain)，不在本章另建一套判断标准。

白话解释：你要把一条候选变成公开成员，得五道门全过——身份、来源、对应、边界、复核。你少一道就只能 pending；尤其不能用本书自己编的 ID 去冒充外部记录 ID，那是假证据。

## 企业行动

团队准备公开一个候选案例时，按以下顺序补证：

1. 由案例证据复核者取得案例级外部记录 ID 和稳定来源定位。
2. 逐项核对原始名称、原始标签、来源记录与示例产物的对应关系。
3. 记录访问日期、证据状态、适用范围和不能支持的结论；有冲突时先降级。
4. 只有在许可明确时才制作公开快照，并同时登记内容哈希；没有许可时不创建快照。
5. 复核公开内容中的身份、结果、敏感信息和传播文案，再把结构化状态改为可发布。
6. 重新生成附录并运行内容校验，让正文计数、成员清单和结构化数据保持一致。

白话解释：你补证时按上面六步走，先拿到外部记录 ID 和稳定来源，再逐条核对、登记局限、确认许可，最后才把状态改成可发布。你没有许可就别存快照，有冲突先降级；每一步都要留痕，否则正文、清单和结构化数据会对不上。

## 边界与下一步

本章是截至 2026-08-01 的内容快照，不对 R11 集合页之外的内部记录作推断，也不把无法稳定定位的卡片内容转录为公开事实。公开数量会随补证、失效或撤回而变化，每次发布都必须重新运行同一发布门。

下一步不是扩写候选故事，而是逐条取得可复核的案例级定位、确认公开许可并记录局限。在此之前，读者可以借助待核验线索理解可能的任务方向，但不能把它们引用为已核验案例。

白话解释：你别把「多写几个候选故事」当成下一步，真正的下一步是逐条拿到能复核的定位、拿到公开许可、记清楚局限。你在这之前只能把线索当方向参考，不能对外写成「已验证案例」。

## 常见问题

**你想引用一个客户案例，但只找到集合页上的名称和标签，够不够？**
不够。你至少要拿到案例级外部记录 ID 和稳定来源定位，五道发布门全过，才算进公开成员清单。只有名称和标签，只能当待核验线索，对外引用会被打回。

**你看到「通过发布门案例为 0」，是不是说 AI 办公没有成功案例？**
不是。它只说本仓库按证据门严格核验后，还没有一条能公开引用的案例。你遇到看着很具体的客户故事，也得先补证，不能默认它已经验证过。

**你能不能把别人的示例页面直接当成自己单位的证据？**
不能。示例页面只证明产物形态，不证明归属、成本或生产稳定性。你哪怕随时能打开它，也不能反推它属于某条候选，更不能写进你的汇报当效果。

**你作为案例证据复核者，补证时第一件事做什么？**
先拿案例级外部记录 ID 和稳定来源定位，再逐条核对名称、标签、来源和产物能不能对应到同一条记录。你没有外部 ID，后面都无从谈起。

**你发现一条候选和原始记录对不上，该停还是该改？**
先降级、保持 pending，并记录冲突继续补证。你别硬把对不上的内容写进公开成员清单，等拿到一致来源再决定能不能发布。
