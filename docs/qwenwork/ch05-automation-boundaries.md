# 自动化边界：让系统可停、可接管、可恢复

## 白话导读

这一章帮你给「自动化」装上一个能随时停下的刹车。你一旦让系统定时跑周报、自动发群消息，最怕的不是它不干活，而是出错后还在继续发、原件被改、没人接手。你团队若没这套刹车，一次字段变化就可能让日报连错一整周；本章给你一张自动化运行卡：停机、人工接管、回退、撤销、恢复五个动作分别管什么，你读完就能在上线前把「谁在异常时接手、原件怎么保住、出错怎么撤回」写清楚。你以后部署自动化，心里有底、出事不慌。

## 30 秒结论

<span id="claim-automation-human-handoff-01" data-claim-id="claim-automation-human-handoff-01"></span>本书主张：自动化只有在异常时能够停止执行、保护原件、通知责任人、转为人工完成并经重新验证后恢复，才具备进入企业运行的基本条件。

白话解释：这条为什么这么定？你部署自动化前最该想清楚的是「它出事时谁接手」。如果一个定时任务跑偏了还在发旧口径结论，损失会比人工慢一点大得多；所以你能不能停、能不能接管、能不能恢复原样，才是它该不该上线的门槛，你要把这三件事当成上线闸门去卡。

- 自动校验、人工复核、交付验收和动作确认是四个不同控制点。
- 停用、人工接管、回退、撤销和恢复处理不同状态，不能混用。
- 写入、发送、发布等高风险动作必须服从治理等级和明确授权。

## 你可能遇到的场景

你想让系统每周自动整理周报或会议纪要：读取本周文件、生成摘要、列出行动项，再发到群里。输入例子是「周五 17:00 前的会议纪要、上周周报和已确认的群聊对象」。你先别急着开定时器，先把停机、人工接管、回退和恢复写进任务；你别等第一次出错才补这些开关——那时原件可能已经改了、消息已经发了。

## 你会拿到什么

你上线前先把这张卡备齐，它最少包含四块，缺一块上线就别放行：

1. 触发条件、输入版本和空数据处理；
2. 自动校验、人审、交付验收、动作确认四个控制点；
3. 停用开关、接管人、备用流程、通知内容和影响范围；
4. 上一稳定版本、重验样本、撤销方式和恢复批准记录。

## 照着做

1. 先用周报或会议纪要跑一次草稿流程，明确哪些步骤只读、哪些步骤会写入、发送或发布。
2. 为日期、行数、总额、重复运行和权限变化设置机器检查，并安排内容复核者与动作责任人。
3. **中间检查点：**故意用缺文件、字段变化或对象不明的输入演练停机；确认系统保留原件、隔离草稿并通知接管人。
4. 用正常、边界、失败样本重验，业务负责人批准影响处理后，才恢复自动调度。

可先看[优克拉：产品研发与考勤算薪](/qwenwork/case-youkela)，把其中的资料核对和高后果人工确认当作运行边界练习；案例陈述不等于你的自动化效果或可无人值守承诺。你拿它当练习素材即可，别把案例里的顺畅当成你自己的验收结论。

## 做完检查

执行一次故障演练：让输入版本不匹配，确认新任务停止、原件未改、责任人收到通知、当前产物标为草稿，并能按备用流程完成交付；否则不得上线。

白话解释：你别跳过这次演练。让输入版本故意对不上，看系统是不是真的停下、真的没动原件、真的通知到人；任一项不满足，它就不能上线，你后面省下的时间会在出事时加倍赔回去。

## 需要注意

发生校验失败、重复运行、权限变化或对象不明时，立即停用并停止外发，保留原件、现场和日志，人工接管当前任务；若新版本失败，回到上一稳定版本，修复后经业务负责人重新确认再恢复。

白话解释：你遇到这几类信号时，第一反应就是「先停、别发、留现场」。原件和日志留住了，后面才有得查、有得退；你别想着先凑合发出去再补，那样往往越错越大。

## 为什么重要

自动化扩大了单次错误的影响范围。字段变化可能让日报连续出错，登录失效可能造成静默缺数，重复调度可能多次发送，界面变化可能让电脑操控点错对象。只准备一个「关闭开关」不能解决已经执行的动作，也不能说明由谁完成剩余任务。

你作为企业 AI 负责人需要把故障处理设计成正常运行的一部分。业务负责人则需要知道，异常出现后原件是否安全、交付是否延期、谁正在接管，以及何时允许重新上线。

白话解释：这节是给管理者看的。你作为业务负责人，真正要问的不是「它能不能跑」，而是「它跑歪了谁顶上、原件还在不在、什么时候能放心恢复」。你把这三点问住了，自动化才算可控。

## 方法或模型

四个控制点分别回答不同问题：

| 控制点 | 固定定义 | 典型证据 | 责任角色 |
|---|---|---|---|
| 自动校验 | 检查机器可判定的格式、范围、完整性和一致性条件 | schema 结果、行数、哈希、勾稽和重复检查 | 工作流 Owner |
| 人工复核 | 判断事实、语义、专业质量和风险是否正确 | 抽查记录、修改清单、专业意见 | 内容复核者或专业 Owner |
| 交付验收 | 决定产物是否满足任务卡并可进入下一环节 | 通过、退回或有条件通过记录 | 业务负责人 |
| 动作确认 | 授权实际发送、写入、发布、删除或其他外部动作 | 确认人、对象、范围、时间和变更清单 | 动作责任人 |

白话解释：这四个点你别混。机器能判的格式、范围归「自动校验」；事实对不对归「人工复核」；能不能进下一环节归「交付验收」；真要发出去、写进去归「动作确认」。你把一个点当另一个点用，责任就糊了。

五个运行术语也不能互相替代：

| 术语 | 含义 | 适用时点 |
|---|---|---|
| 停用 | 阻止新的自动运行开始 | 发现系统性风险或需要维护时 |
| 人工接管 | 由责任人接手当前未完成任务 | 当前交付仍需按时完成时 |
| 回退 | 切换到上一稳定版本、规则或人工流程 | 新版本失败且尚可使用既有路径时 |
| 撤销 | 在系统支持且风险可控时反向处理已完成动作 | 错误写入、发送或发布已经发生后 |
| 恢复 | 修复、重验和批准后重新开放自动运行 | 根因已处理且恢复条件满足时 |

白话解释：停用、接管、回退、撤销、恢复五件事不是一回事。你停了不等于撤回了已发的消息，回退了不等于撤销了错误写入；所以每张运行卡要把五者各自什么时候用、谁批准写明白，别用一个词含糊带过。

最小接管与恢复链固定为：

1. **触发条件**：自动校验失败、输入异常、权限变化、重复运行或人工报告事件。
2. **停止执行**：阻止新任务和剩余高风险动作，不继续尝试未知步骤。
3. **保护原件**：保留输入、现场、日志和未修改的原文件，隔离错误产物。
4. **通知责任人**：说明影响范围、当前状态、截止时间和需要的决定。
5. **人工完成**：由指定接管人按备用流程完成必要交付，并记录人工变更。
6. **定位失败**：区分输入、权限、工具、规则、模型和环境原因。
7. **修正版本**：创建新版本，不覆盖失败版本和证据。
8. **重新验证**：用正常、边界和失败样本重跑自动校验及人工复核。
9. **批准恢复**：业务负责人确认影响已处理，工作流 Owner 再开放调度。

G2/G3 动作的具体确认规则以第 11 章为唯一规范来源；本章只要求自动化能够调用相应确认和接管机制。

## 案例与证据

官方帮助中心分别说明桌面端定时任务、电脑操控和 IM 频道等能力。 [R5](/qwenwork/appendix-sources#r5) [R6](/qwenwork/appendix-sources#r6) [R7](/qwenwork/appendix-sources#r7) 能力入口和可用范围可能变化，应在当前账号、系统版本和组织授权下实测。

以周一经营日报为例：调度开始前检查输入目录和日期；生成后自动勾稽总额；内容复核者检查异常解释；业务负责人验收；发送群消息前由动作责任人确认。你若遇到字段变化导致勾稽失败，要确认系统真的停在草稿状态、保留原表并通知接管人，不得继续发送旧口径结论。

## 企业行动

为一个已有自动化补齐运行卡：

| 必填项 | 最小内容 |
|---|---|
| 触发与输入 | 调度规则、输入位置、日期范围、空数据处理 |
| 四个控制点 | 各自条件、责任人、证据和超时处理 |
| 故障处置 | 停用开关、接管人、备用流程、影响通知 |
| 版本恢复 | 上一稳定版本、重验样本、恢复批准人 |
| 已执行动作 | 是否可撤销、撤销责任人、不能撤销时的补救方式 |

白话解释：你给已有自动化补这张卡时，最难填的往往是「已执行动作能不能撤销」。你尽早想清楚：发出去的消息撤不回怎么办、写进去的数据怎么补，比上线后再手忙脚乱强得多。

你看到这些信号立刻停用并接管：机器校验失败却仍准备外发；输入范围或账号权限突然变化；相同任务重复运行；原件可能被覆盖；当前动作无法确认对象和影响；没有可联系的责任人或备用流程。

## 边界与下一步

并非所有任务都适合定时或无人值守。你判断来源不稳、验收靠专业判断、失败不可逆或影响外部对象的任务，应保留人在回路中；低风险读取和草稿生成也仍需失败提醒与运行记录。

你判断一个任务该不该无人值守，就看来源稳不稳、验收靠不靠专业判断、失败可不可逆、会不会影响外部对象。本章定义运行控制，不定义组织治理等级；治理章节将统一说明数据敏感度、人机责任和高风险动作门槛。

## 术语翻成人话

| 术语 | 人话 |
|---|---|
| 自动化运行卡 | 你给一个定时任务写的「说明书+安全绳」，写清谁接手、怎么停、怎么退 |
| 自动校验 | 机器能判的格式、范围、勾稽检查，它只管「对不对得上」，不管「对不对」 |
| 动作确认 | 真要发出去、写进去、删掉前的那次授权，是最高风险的一道闸 |
| 停用 | 拦住新的自动运行，等于先喊停，但已经发出的动作还在 |
| 回退 | 切回上一个能用的版本或人工流程，不等于撤回已发生的错误 |
| 撤销 | 在系统支持时反向处理已完成的写入、发送或发布，往往有条件且有时限 |
| 恢复 | 根因修好、重验通过、负责人批准后，才重新放开自动调度 |

## 常见问题

**你该怎么判断一个自动化任务能不能上线？**
你先做一次故障演练：故意让输入版本不匹配，看它是不是真的停下、原件是不是没动、责任人是不是收到通知、草稿是不是能按备用流程交付。四项全满足才上线，任一项不满足都先别放。

**你部署自动化时，最容易漏掉哪一道控制点？**
最容易漏的是「动作确认」。你常把发送、写入当成流程自然结果，忘了它是最该明确授权的高风险动作；谁确认、确认什么对象、什么范围、什么时间，都要写进运行卡。

**跑歪了但消息已经发出去了，你该怎么办？**
你先停用、留现场和日志，再走「人工接管→回退→撤销」。注意回退不等于撤销：已发的消息要单独撤回，已写的数据要单独补正，能撤就撤，不能撤就说明补救方式。

**你作为业务负责人，这一章要你留什么证据？**
至少三样：接管人和备用流程是谁、上一稳定版本在哪、恢复由谁批准。没有这些，异常发生时你只能临时抓人，交付延期还说不清责任。

**哪些任务你不该做成无人值守自动化？**
来源不稳、验收靠专业判断、失败不可逆或会影响外部对象的任务，你都该把人留在回路里；哪怕是低风险读取，也得有失败提醒和运行记录，不能静默跑。
