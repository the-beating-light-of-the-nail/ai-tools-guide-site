# 案例：公众号文章→飞书知识库全自动流水线

> 改编自 TRAE 官方论坛用户 HancksLiu（产品经理）的实战帖[《我用 TraeWork 打造「公众号文章→飞书知识库」全自动流水线》](https://forum.trae.cn/t/topic/172002)（2026-07）。配套技能已开源：[yucai0302/wechat-to-feishu-kb](https://github.com/yucai0302/wechat-to-feishu-kb)。

## 三个痛点

1. **微信生态封闭**：通用爬虫抓公众号返回空壳页面或提示"需在微信客户端打开"，AI 搜索引擎无法穿透微信 CDN 防护，"一键收藏"类工具对公众号基本无效；
2. **阅读与沉淀割裂**：文章收藏了就再也没打开过，无法纳入个人或团队知识库检索复用；
3. **手动整理太贵**：一篇 5000 字文章手动归档 15-20 分钟，每周 10-15 篇，光归档就要 3-4 小时。

## 方案架构：两个 Skill + 双模式

```text
Skill 1  wechat-article-saver     抓取公众号文章 → 存本地 Markdown
Skill 2  wechat-to-feishu-kb      本地 Markdown → 飞书知识库
─────────────────────────────────────────────
即时模式：聊天中直接发文章链接 → Skill 自动触发抓取 + 写入
批量模式：链接逐行贴进 pending.txt → 每晚 22:00 定时任务自动处理
```

### 抓取：四层降级策略

微信公众号的反爬是核心难点，Skill 内置了四层降级，任一层成功即继续：

1. Playwright + Chromium 无头浏览器渲染；
2. HTTP fetch 带反爬 Header（User-Agent、Accept-Language 等）;
3. TraeWork 内置 WebFetch 工具；
4. 手动粘贴原文兜底。

正文用 Mozilla Readability 提取、Turndown 转 Markdown，单篇约 30 秒。

### 沉淀：飞书对接

飞书侧只用了 lark-cli 的两个能力：`wiki + node-create`（建知识库节点）和 `docs + update`（写文档内容）。本地同时保留 Markdown 双备份，可被 Obsidian / Notion / Logseq 直接索引。

## 效果

| 指标 | 之前 | 之后 |
| --- | --- | --- |
| 单篇整理 | 15-20 分钟 | 5 秒（即时）/ 0 秒（定时） |
| 每周节省 | — | 3-4 小时 |
| 每月节省 | — | 约 15 小时 |
| 知识可检索 | 收藏夹里吃灰 | 100%（飞书 AI 问答 + 本地全文搜索） |
| 团队复用 | 无 | 知识库全员可访问 |

## 最重要的一课：定时任务的提示词

作者第一次配定时任务时只写了一句"抓取文章存知识库"，**失败**——缺少 space_id、认证方式、文件路径等参数。修正后的认知：

> **定时任务本质上是一个「无人值守的对话」，提示词越详细，越稳定。**

把完整执行步骤、参数、错误处理逻辑全部写进任务说明后一次跑通。详见[自动化定时任务](/traework/07-automated-tasks)的写作清单。

## 迁移到你的场景

这条流水线的骨架是通用的：

```text
信息源（链接/邮件/报表）→ 抓取 Skill（多层降级）→ 标准化中间格式
→ 沉淀 Skill（飞书/Notion/本地知识库）→ 定时调度 + 即时对话双模式
```

可替换的信息源：行业资讯页、竞品 changelog、应用商店评论、团队周报邮件。作者也坦承现状的局限——本地 pending.txt 的收集方式"还不够智能"，理想的自动推荐受限于微信生态的封闭性。

## 安全提醒

- 抓取流程涉及登录凭证时，勿在公共设备操作；
- 尊重内容版权：归档自用与二次分发是两回事，团队知识库注意授权边界。
