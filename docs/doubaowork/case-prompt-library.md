# 分类太细反而难找：541 个 GPT 提示词案例重新归类

> 场景：收集 GPT-Image2 提示词案例时总觉得越多越好，攒到 541 个问题也来了——案例散在 GitHub 仓库、README 和本地文件夹，分类越分越细，想找一条"国风水墨海报"得在几个类之间来回翻。

> 前置条件：豆包与飞书账号一致；项目资料已上传飞书云盘或知识库（可 @ 引用文档、云盘文件、联系人和历史对话）。

原来的管理方式：案例全堆在 README 和 gallery 文档里手动分了 13 类；风格标签 19 个、场景标签 10 个，三套维度互相交叉；本地文件和 GitHub 版本经常对不上。**这套分类是按时间顺序搭的，从没站在检索者的视角设计过——分类维度越叠越多，最后反而变成查找的最大障碍。**

## 第一步：一句话让豆包开始干活

资料收拢进飞书后，全程不用写复杂提示词：

```text
帮我分析这个项目的案例分类体系 @awesome-gpt-image-2 项目资料
先看看现有分类有什么问题，再根据真实搜索词重新设计
```

它会自动读案例数据、统计分类分布、找出同义词和交叉项。

## 第二步：量化诊断现有分类的五个硬伤

1. **同义词标签满天飞**：19 个风格标签里 `Character` 用了 113 次、`Characters` 只用 2 次——完全同一个东西；`Product`/`Products`、`Infographic`/`Charts`、`Realistic`/`Photography` 全是重复，19 个标签其实 12 个就够；
2. **同一概念出现在三个维度**："海报"在 category 和 styles 里都有，"历史"在三层都出现——用户不知道从哪个入口找；
3. **垃圾桶分类**：`Other Use Cases` 塞了 28 个案例，啥都有，等于没分类；
4. **薄分类撑不起一级目录**：4 个一级分类合计才占 11% 的案例；
5. **内部术语用户看不懂**：`R&D`、`Prompt as Code` 这类词，普通用户搜索时根本不会用。

更关键的一步：它从 541 个案例的真实标题里提取高频搜索词，**反向推导用户的真实检索习惯**——搜"海报/封面/宣传"82 次、"信息图/技术图解"48 次、"界面/截图/App"38 次、"人像/肖像/头像"28 次、"插画/国风/水墨"25 次。用户打开提示词库时带着明确的落地目标："我要做一张 XX 图"。**分类体系围绕产出物来搭，分类名直接对应用户要完成的最终目标**——这是整个重构的核心支点。

## 第三步：从真实搜索词出发重新设计

新分类 **13 个 → 8 个，全部按产出物命名**，合计 541 个一个不多不少、没有垃圾桶。合并逻辑：

- **界面与信息图**：UI、Dashboard、信息图、技术图解在用户心智里都是"结构化信息"，合在一起 140 个是最大类；
- **插画与艺术**：国风/古风/水墨/历史题材本质是插画艺术风格，并入后"国风"通过别名直接命中；
- **场景·空间·叙事**：建筑、城市、故事板、世界场景都是"大空间/世界观"类产出物；
- **角色与人物**：专指虚拟角色/卡牌/3D 角色，真实人像归"摄影与写实"；
- **Other Use Cases 拆散**：28 个案例逐条归入对应分类。

分类精简了，但搜索不能丢：给每个分类配**别名表**——搜"国风/古风/水墨"→ 插画与艺术，搜"人像/肖像/头像"→ 摄影与写实，搜"Logo/VI/标志"→ 品牌与标志，搜"详情页/包装/主图"→ 商品与电商视觉。

## 第四步：批量迁移到飞书知识库

在知识库按 8 个新分类建一级目录，然后：

```text
按照新分类映射表，把 cases.json 里的 541 个案例重新打 category 标签
然后按 8 个分类批量创建飞书文档，放到对应的知识库目录下
旧的分类锚点保留跳转，不要删
```

它会批量改写 category 字段、调用飞书接口批量建文档归入目录、旧 URL 锚点保留跳转（收藏的旧链接不失效）、案例 id 和图片路径不变（GitHub 链接不断）。**不要一次性全量改**：分阶段来——先改标签（低风险）→ 再改分类（中风险）→ 最后改前端展示和文档，每一步都能回滚。

## 第五步：用真实查询测试

| 真实查询 | 旧结构 | 新结构 |
| --- | --- | --- |
| 国风水墨海报 | 在 History 和 Illustration 之间犹豫 | 直接插画与艺术，一步命中 |
| 写实人像 | Photography 和 Characters 之间犹豫 | 摄影与写实，别名"人像"直达 |
| App 界面截图 | UI 分类内混有 Poster 内容形成干扰 | 直接进入界面与信息图 |
| 角色卡牌 | 3D 卡牌散在 Illustration 里 | 角色与人物，命中更集中 |
| 城市建筑地图 | Architecture 和 Scenes 间来回犹豫 | 场景·空间·叙事 |

10 条测试查询里，5 条完全消除了多分类间反复跳转的犹豫，4 条命中路径更短，1 条语义匹配精度明显提升。后续迭代接入了 GA4 真实搜索日志，基于真实用户行为再校准一次别名映射表——只需微调别名规则，不用推翻已验证的分类架构。

## 分阶段迁移清单

| 阶段 | 做什么 | 风险 |
| --- | --- | --- |
| 0 | 导出真实搜索词，校准别名表 | 只读 |
| 1 | 合并同义标签（Characters→Character 等） | 低 |
| 2 | 按映射表批量改写 category 字段 | 中 |

最大的感受：**知识库管理以前是体力活，现在变成了动动嘴的事**——豆包负责读数据、跑统计、找问题、设计方案、批量迁移，人只在关键节点做判断和确认。老项目沉淀的经验不用一直闲置，用 AI 搭配飞书知识库把它盘活，落地过程比想象中顺利很多。
