# 哪些知识已经过期，自动找到 Owner 确认

> 场景：知识库能解决信息存放的问题，却无法保证资料始终有效。一份几年前的攻略，门票价格、开放时间、交通线路和预约规则都可能变了——**跳过核验直接使用，资料越详细，越容易让人相信过时的结论**。

以旅游规划为例：知识库里有一份 2013—2014 年的《上海旅游攻略 PDF》写着"东方明珠门票 100 元、地铁只有 11 条线"，实际 2026 年二球联票 199 元、地铁已超 20 条线；联系人向明分享的《上海旅游避坑指南（2026 版）》又说老攻略推荐的城隍庙小吃广场"贵且难吃"。真要手动逐条核验，至少两三个小时。

## 提示词：把核验要求写进去

简短版（交代出行时间、目的地和输出格式）：

```text
我准备下周五去上海旅游，请给我规划一个 3 天 2 晚的行程。
结合我飞书中的相关信息（知识库、聊天记录），为我量身定制旅游行程，
最后以 HTML 格式输出。请标注引用来源，并充分核实信息是否已经过期。
```

完整版把资料范围、核验要求、冲突处理和交付标准补齐：

```text
我准备下周五去上海旅游，请帮我规划 3 天 2 晚的行程。
结合我飞书知识库中的旅游攻略（Wiki 链接：【链接】），
以及联系人向明分享的《上海旅游避坑指南（2026 版）.xlsx》。

要求：
1. 先读取知识库和联系人文件，识别哪些信息已经过期（如门票价格、开放时间、
   地铁线路），哪些仍然有效。
2. 对于过期或相互冲突的信息，单独标注并找资料提供者或负责人确认，
   不要静默替换。
3. 结合 2026 年的实时信息（天气、高铁时刻、景点预约要求、近期展览）
   进行核验和更新。
4. 输出 HTML 行程方案，包含每日详细行程、交通、住宿、美食、预算和雨天备选。
5. 每条关键信息标注来源（知识库 / 向明 / 实时网络）和核实时间。
6. 出发前 48 小时提醒我再次确认天气和景点临时公告。
```

## 它怎样推进

1. **先确认数据源**：读取飞书知识库的历史攻略、联系人分享的避坑指南和相关聊天记录——先确定"手上有哪些资料"，避免规划只依赖某一份攻略；
2. **提取易变信息重点核验**：门票价格、开放时间、地铁线路、高铁车次、预约规则和近期展览；旧攻略与新指南说法不一致时，**保留不同说法及各自来源**，不静默替换；天气、车次和景点公告等实时信息联网核验；
3. **合并后才组合行程**：旧攻略中仍有价值的路线经验 + 2026 版避坑指南的实际建议 + 当次查询的天气交通信息，放进同一份方案。

## 结果长什么样

**核心信息速览**先判断框架：9 月 4—6 日 3 天 2 晚；去程 G256（431 元）返程 G3092（390 元）；住人民广场或南京东路（1/2/8 号线，步行可到外滩）；人均约 2500—3200 元。**三天主线**：D1 抵达 → 南京路 → 外滩夜景；D2 上海博物馆 → 豫园 → 2 元轮渡过江 → 陆家嘴；D3 武康路 → 安福路 → 本帮菜 → 新天地 → 返程。

结果还说明了各类资料的用法，方便追溯每项建议的依据：2013 年 PDF 的**价格和门票已过期**，但**路线逻辑和美食文化仍有参考价值**；向明指南的 48 条建议中适合本次的已融入每天安排（选 2 元轮渡、去北外滩观景、避开人流集中的网红餐厅）。当次查询显示三天都有小雨，方案里同时安排了浦东美术馆、上博东馆等雨天备选，并提醒出发前 48 小时再次确认天气和临时公告。

完整的 **HTML 行程**把每天的时间段、交通路径、景点预约、餐饮建议、预算和雨天备选放进同一个页面——避坑建议挂在对应的景点、交通和餐饮环节，并保留资料来源：读者知道某条建议的依据，情况变化时也能回到原始资料重新确认。

## 启发

这个例子展示的是**过期知识的治理方法**：保留旧资料中仍有价值的经验，对易变信息重新核验，对来源冲突的内容保留依据和确认入口（找资料提供者/Owner 确认，而不是静默替换）。这样整理后，知识库才能持续为当下的任务提供可用信息。实际用于出行时，还可以补充酒店预算、饮食忌口、步行强度、必去景点，让它进一步缩小选择范围。
