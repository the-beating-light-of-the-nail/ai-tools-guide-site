# 專案結束，把文件、決策和交付物一起沉澱

> 場景：給 WeSight（桌面應用）接入 PI 引擎。以前總覺得讓 AI 寫程式不難，難的是讓 AI 真正「懂」你的專案——這次豆包工作把專案知識庫和程式碼放在一起看，把要動的地方規劃得清清楚楚。

訴求一句話就能交代：

```text
在 wesight 這個專案中，準備添加引擎。我想用 PI Agent 引擎。
現在請結合知識庫的內容和程式碼的現狀，PI 引擎的接入，給我出一個執行計畫。
```

## 知識庫 + 程式碼一起看

豆包工作先翻了兩樣東西：**飛書裡的專案知識庫**，和**程式碼倉庫裡的引擎路由、常量定義、適配器、Provider 註冊**這些接入點——同步對齊沉澱的專案歷史上下文和實際運行的架構細節，再決定計畫怎麼寫。

一個意外發現：它第一句話就提醒**知識庫是空的**——只有標題和一個指向已刪除子頁面的引用。引用這個知識庫的人以為裡面有答案，其實什麼都沒有。更讓人放心的是，它沒有因為知識庫空就瞎編，而是明確說明「計畫裡的 PI 資訊全部來自對 pi.dev 官方文件和 badlogic/pi-mono 原始碼的第一手調研」，把資訊來源交代得清清楚楚。

> **知識會過期，缺來源、負責人和更新時間後，舊答案會長期誤導使用者。**一個空殼知識庫比沒有更危險——它讓每個引用它的人都誤以為「這裡有沉澱」。

從程式碼現狀它反向摸清了新增引擎要逐層打通的 5 個環節：常量/類型註冊 → Provider/環境/安裝器 → 執行時適配器 → Router + Main 接線 → Renderer UI，最後補配置同步和全鏈路測試。幾個關鍵決策都給了明確建議：整合通道走 RPC 模式（`pi --mode rpc`，stdin/stdout JSONL 協議）；新建獨立適配器 `PiRuntimeAdapter`（不複用為解析 CLI 文字輸出定製的 131KB 適配器，PI 是乾淨的 JSONL 流）；首版權限直通、二期再接確認彈窗。

## 交付物：一份可落地的執行計畫

計畫存到 `docs/pi-engine-integration-plan.md`，按 4 個里程碑排了實施順序和預估工作量：

1. **M1 骨架**：常量/類型/Provider/安裝器——能編譯，環境面板出現 Pi 並可偵測/安裝；
2. **M2 核心跑通**：PiRuntimeAdapter + Router + Main 接線——跑通一輪對話；
3. **M3 完整功能**：UI + 配置同步 + 圖片/續聊/停止；
4. **M4 權限打磨**：權限彈窗 + 測試與回歸。

還提前列了 6 個風險點（models.json 的 schema、串流語義、會話續聊策略、Windows 相容等）。決策不拍腦袋：三個核心決策點清晰呈現、附驗證過的預設方案參考，**最終決策權完整交還給開發者**——先完成全鏈路方案推演、再保留核心決策空間，大幅降低溝通內耗。

## 把調研和交付物沉澱回知識庫

讓它把調研文件沉澱進專案知識庫時，它識別出當前帳號只有唯讀權限，隨即自動切換路徑匯入個人知識庫，並完成全量內容校驗。這個過程點出一個容易被忽略的認知：**文件的存放位置和可維護權限本身就是專案資產的一部分**——如果每份文件都沒標註負責人和最後更新時間，知識庫很快會變成沒人認領、沒人敢改的資訊孤島。

要求「先只做表層骨架，不要真實開發，做完同步到飛書文件」時，它也精準對齊：常量、類型、空適配器、UI 選項都加上，能編譯、介面能看到 PI 選項，但不實現真實 RPC 通訊。

## 一個健康的專案知識庫長什麼樣

```text
專案知識庫
├── 首頁
├── 產品與架構
├── 研發規範
├── 會議與決策
│   ├── 會議紀要
│   └── 決策記錄 (ADR)
├── 發布與版本
│   ├── 發布記錄
│   └── 發布檢查清單
└── 團隊與職責
```

**專案結束，把文件、決策和交付物一起沉澱；沉澱時記得寫上來源、負責人和更新時間。**這樣，AI 和後來的同事才不會拿著過期的答案走遠路。AI 越來越強，上下文（context）就越來越重要。
