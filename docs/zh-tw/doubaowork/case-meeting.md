# 一場會議，從會前準備到待辦落地

> 場景：會開完了，事情卻不一定跟著落地。用 AI 把「記過了」變成「有人接、有截止、可檢查」。

會開完了，事情卻不一定跟著落地：討論了不少內容，群裡留下幾句「回頭跟進」，散會後再問誰負責、什麼時候完成，大家往往還得重新翻記錄。哪些話已經形成決定，哪些還只是想法，哪些任務要馬上交給具體的人？先把這些分清楚，紀要才不會停在「記過了」。

一場會議可以拆成三段：**會前**讓參與者帶著同一份背景進入討論，**會中**保留原始記錄，**會後**把決定和行動項交給具體的人。紀要只是中間一步，還要連接上週任務和下次檢查。

在整個流程裡，模型適合處理**整理、對照和提取**；負責人、截止時間、延期原因和最終決策仍以原始材料為準。材料裡沒寫清楚的地方，保留「待確認」比補一個完整答案更安全。

## 逐字稿整理成標準會議紀要

逐字稿裡常見口頭語、重複討論和臨時岔話，直接壓縮很容易把結論一起壓掉。整理時先識別議題，再分別提取討論依據、明確決定、行動項和仍有分歧的事項：

```text
請閱讀附件《產品週會逐字稿.docx》，將其整理成一份正式會議紀要。
請刪除口頭語、重複表達和與會議無關的內容，但不要改變發言人的原意。
紀要需要包含會議主題、時間、參會人、會議背景、議題討論、明確結論、
已確認決策、行動項和待確認事項。
只有原文明確提到的負責人和截止時間才能填寫。
原文沒有說明的內容請標記為「待確認」，不要自行推測。
```

執行時，系統會刪去口頭語和重複討論，再按會議背景、議題、結論、決策、行動項和待確認事項整理。如果拿到的是**原始音訊**，也可以先轉成逐字內容再按同樣結構整理——省去手動轉寫，但辨識結果仍需結合會議上下文複核。

> 提醒：人名、產品名、數字和否定表達容易影響結論。正式分發前最好回聽對應片段，確認系統沒有把「討論意見」寫成「最終決定」。

## 跟蹤上次會議任務

單篇紀要解決的是「本次發生了什麼」，兩週材料放在一起才能回答「事情有沒有推進」。核對時逐項沿用上週的行動項名稱，再從本週逐字稿裡找**完成證據、延期說明或取消決定**——沒被提到的任務不能自動算作完成：

```text
請同時閱讀《上週會議紀要.docx》和《本週會議逐字稿.docx》。
逐項核對上週會議中的行動項，並根據本週會議內容判斷其狀態：
已完成、進行中、延期、取消和未提及。
對於延期任務，請提取延期原因、新的截止時間和責任人；
對於本週新增任務，請單獨列出。
最後生成「上週任務跟蹤表」和「本週新增行動項」兩個部分。
```

系統會把上週行動項逐條拿到本週內容中核對，再把本週新增任務單獨列出——兩組內容分開，舊任務不會和新任務混在一起。驗收時檢查：每項舊任務是否都有狀態；延期任務有沒有原因、新截止時間和責任人；新增行動項是否確實來自本週會議。
