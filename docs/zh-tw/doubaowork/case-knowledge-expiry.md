# 哪些知識已經過期，自動找到 Owner 確認

> 場景：知識庫能解決資訊存放的問題，卻無法保證資料始終有效。一份幾年前的攻略，門票價格、開放時間、交通線路和預約規則都可能變了——**跳過核驗直接使用，資料越詳細，越容易讓人相信過時的結論**。

以旅遊規劃為例：知識庫裡有一份 2013—2014 年的《上海旅遊攻略 PDF》寫著"東方明珠門票 100 元、地鐵只有 11 條線"，實際 2026 年二球聯票 199 元、地鐵已超 20 條線；聯絡人嚮明分享的《上海旅遊避坑指南（2026 版）》又說老攻略推薦的城隍廟小吃廣場"貴且難吃"。真要手動逐條核驗，至少兩三個小時。

## 提示詞：把核驗要求寫進去

簡短版（交代出行時間、目的地和輸出格式）：

```text
我準備下週五去上海旅遊，請給我規劃一個 3 天 2 晚的行程。
結合我飛書中的相關資訊（知識庫、聊天記錄），為我量身定製旅遊行程，
最後以 HTML 格式輸出。請標註引用來源，並充分核實資訊是否已經過期。
```

完整版把資料範圍、核驗要求、衝突處理和交付標準補齊：

```text
我準備下週五去上海旅遊，請幫我規劃 3 天 2 晚的行程。
結合我飛書知識庫中的旅遊攻略（Wiki 連結：【連結】），
以及聯絡人嚮明分享的《上海旅遊避坑指南（2026 版）.xlsx》。

要求：
1. 先讀取知識庫和聯絡人檔案，識別哪些資訊已經過期（如門票價格、開放時間、
   地鐵線路），哪些仍然有效。
2. 對於過期或相互衝突的資訊，單獨標註並找資料提供者或負責人確認，
   不要靜默替換。
3. 結合 2026 年的即時資訊（天氣、高鐵時刻、景點預約要求、近期展覽）
   進行核驗和更新。
4. 輸出 HTML 行程方案，包含每日詳細行程、交通、住宿、美食、預算和雨天備選。
5. 每條關鍵資訊標註來源（知識庫 / 嚮明 / 即時網路）和核即時間。
6. 出發前 48 小時提醒我再次確認天氣和景點臨時公告。
```

## 它怎樣推進

1. **先確認資料來源**：讀取飛書知識庫的歷史攻略、聯絡人分享的避坑指南和相關聊天記錄——先確定"手上有哪些資料"，避免規劃只依賴某一份攻略；
2. **提取易變資訊重點核驗**：門票價格、開放時間、地鐵線路、高鐵車次、預約規則和近期展覽；舊攻略與新指南說法不一致時，**保留不同說法及各自來源**，不靜默替換；天氣、車次和景點公告等即時資訊聯網核驗；
3. **合併後才組合行程**：舊攻略中仍有價值的路線經驗 + 2026 版避坑指南的實際建議 + 當次查詢的天氣交通訊息，放進同一份方案。

## 結果長什麼樣

**核心資訊速覽**先判斷框架：9 月 4—6 日 3 天 2 晚；去程 G256（431 元）返程 G3092（390 元）；住人民廣場或南京東路（1/2/8 號線，步行可到外灘）；人均約 2500—3200 元。**三天主線**：D1 抵達 → 南京路 → 外灘夜景；D2 上海博物館 → 豫園 → 2 元輪渡過江 → 陸家嘴；D3 武康路 → 安福路 → 本幫菜 → 新天地 → 返程。

結果還說明了各類資料的用法，方便追溯每項建議的依據：2013 年 PDF 的**價格和門票已過期**，但**路線邏輯和美食文化仍有參考價值**；嚮明指南的 48 條建議中適合本次的已融入每天安排（選 2 元輪渡、去北外灘觀景、避開人流集中的網紅餐廳）。當次查詢顯示三天都有小雨，方案裡同時安排了浦東美術館、上博東館等雨天備選，並提醒出發前 48 小時再次確認天氣和臨時公告。

完整的 **HTML 行程**把每天的時間段、交通路徑、景點預約、餐飲建議、預算和雨天備選放進同一個頁面——避坑建議掛在對應的景點、交通和餐飲環節，並保留資料來源：讀者知道某條建議的依據，情況變化時也能回到原始資料重新確認。

## 啟發

這個例子展示的是**過期知識的治理方法**：保留舊資料中仍有價值的經驗，對易變資訊重新核驗，對來源衝突的內容保留依據和確認入口（找資料提供者/Owner 確認，而不是靜默替換）。這樣整理後，知識庫才能持續為當下的任務提供可用資訊。實際用於出行時，還可以補充酒店預算、飲食忌口、步行強度、必去景點，讓它進一步縮小選擇範圍。
