# 個人 IP 怎麼做 GEO 體檢

> 場景：判斷一個 IP 有沒有被看見，以前是搜名字、看粉絲數；現在多了一道新入口——**越來越多人直接問 AI**。AI 能不能把你的中文名和英文帳號對上？會不會把同名專案安到你頭上？它引用的是本人主頁，還是轉了幾手的聚合文？

這些問題靠隨手問一句"你知道某某嗎"測不出來——問題不固定、時間不固定、判斷標準也不固定。實測用一套固定流程做了一次完整體檢：**先準備公開事實基準卡和 5 個固定問題 → 逐題公開檢索、核對來源、評分 → 生成監測表和修正建議**。本次結果 29/30：沒有完全沒認出來或明確說錯的問題，但發現 1 個身份混淆風險和 1 個來源品質問題。

## 先把邊界說清：這是檢索資訊

這套流程只做三件事：讀取本人確認可以公開的事實、檢查公開網頁、生成本地報告。它不會自動修改主頁，不替你發聲明，也不能保證改完簡介後所有 AI 立刻換說法——搜尋結果會變、模型版本會變。所以結果只代表"某一天、某個助手、簡體中文口徑下的一次實測"。另外：**粉絲數、Star 數、榜單名次這類會變的數字，可以作為當天快照，但不應被當成不變的身份事實**。

工具用最小組合：「VOC 與輿情調研」Skill（多來源公開檢索、資訊歸類、來源回溯）+ 內建公開檢索。不需要額外接搜尋連接器，也不必橫向比較多個 AI 助手（變數太多）。

## 準備兩份輸入材料

**公開事實基準卡**——只寫自己能確認、也願意公開的穩定事實：首選公開名稱和常用英文帳號；對外身份和長期分享主題；本人公開主頁；可核驗的代表專案；以及**明確不納入基準的內容**（真實姓名、聯絡方式、動態粉絲數、未確認頭銜）。

**固定監測問題**（本次 5 個，分別測：能否認出實體、認清帳號歸屬、找到代表內容、對上中英文名稱、會不會被同名專案帶偏）：

1. 某某是誰？主要公開分享什麼內容？
2. 某某有哪些可以確認屬於本人的公開帳號和代表專案？
3. 如果我想學習【你的主題】，某某有哪些公開資料可以參考？
4. "中文名"和"英文帳號"是不是同一個創作者？請給出可核驗的公開來源。
5. 某某有沒有公開分享過【細分主題】？如果有，專案是什麼？

## 實測提示詞

口徑、評分、來源優先順序和安全邊界一次寫清：

```text
我負責維護個人 IP"【你的公開名稱 / 英文帳號】"的公開資訊。
請使用"VOC 與輿情調研"能力，完成一次可復現的 AI 答案可見度檢查。

輸入材料：
1. 公開事實基準卡：【ip-baseline.md 路徑】
2. 固定監測問題：【audit-questions.md 路徑】

檢查口徑：
- 助手：豆包工作當前對話
- 日期：【填寫實測日期】
- 語言：簡體中文
- 只檢查公開網頁，不讀取私人帳號資料，不搜尋或推斷聯絡方式、住址、收入等私人資訊。

請按下面步驟執行：
1. 先讀取兩個輸入檔案，確認基準事實和固定問題完整。
2. 對每個問題獨立進行公開檢索，像第一次遇到這個名字一樣回答，不要只照抄基準卡。
3. 每個問題記錄：原始問題、回答摘要、是否正確識別公開名稱、是否與英文帳號對上、
   事實錯誤或缺失、引用 URL、來源類型、訪問情況和檢索時間。
4. 將問題級結果分成四類：未出現、描述錯誤、身份混淆、來源品質差；
   如果沒有問題也要明確寫"未發現"。
5. 來源優先順序按"本人公開主頁或本人專案 > 明確署名的公開報道 > 聚合頁或轉載頁"判斷。
   第三方頁面不能單獨證明帳號歸屬。
6. 給每個問題按三項各 0—2 分：實體是否出現、身份是否準確、來源是否可靠；
   同時保留文字理由，不只給總分。
7. 彙總哪些公開資訊已被穩定看見，哪些缺少一致、可引用的公開頁面。
   修正建議必須落到具體頁面和具體欄位，例如主頁簡介、專案 README、作者頁之間如何統一；
   不要承諾修改後一定影響模型答案或排序。
8. 做一次自檢：每個結論能否回到 URL；是否把一次實測外推成所有 AI 助手；
   是否把第三方資訊寫成本人確認事實。

最終請交付兩個檔案：
- 《個人IP_AI答案可見度監測表.md》：口徑、逐項結果、評分、來源和限制。
- 《公開資料修正建議.md》：按 P0 / P1 / P2 排序，寫清建議修改的公開頁面、
  當前問題、建議動作和複測方法。

聊天裡只彙總：總分、四類問題分別出現幾次、最需要先修正的 3 個公開資訊點。

安全邊界：只做唯讀檢查和生成本地檔案；不要修改任何公開主頁或專案，不要發布內容，
不要傳送訊息，也不要承諾能夠操縱模型答案。
```

執行時注意三件事：它有沒有**真的開啟公開頁面**而不是隻憑模型記憶；帳號歸屬有沒有**本人主頁或本人專案**作證據；第三方轉載有沒有被誤寫成"本人確認事實"。比如"一個第三方頁面說這個帳號屬於某人"證據不夠——更穩的鏈路是本人 GitHub 專案連結到 X，X 主頁也回鏈 GitHub，兩個公開頁面互相驗證。

## 實測結果：29/30，不是滿分反而更有用

| 問題 | 實體出現 | 身份準確 | 來源可靠 | 小計 |
| --- | --- | --- | --- | --- |
| Q1 是誰、分享什麼 | 2 | 2 | 2 | 6/6 |
| Q2 公開帳號和代表專案 | 2 | 2 | 1 | 5/6 |
| Q3 學習資料 | 2 | 2 | 2 | 6/6 |
| Q4 中英文名是否同一人 | 2 | 2 | 2 | 6/6 |
| Q5 細分主題專案 | 2 | 2 | 2 | 6/6 |
| **合計** | **10/10** | **10/10** | **9/10** | **29/30** |

四類問題分佈：未出現 0、描述錯誤 0、身份混淆 1、來源品質差 1。真正值得處理的是 3 個 P0 修正點：

1. **GitHub 主頁 Bio 為空**——帳號能被找到，但主頁沒直接寫中文名稱和身份，AI 要繞到倉庫 README 才能建立關聯；
2. **X 帳號缺少可獨立驗證的 GitHub 回鏈**——只有 GitHub 對 X 的單向宣告，沒有驗證到反向連結；
3. **存在同名近似專案**——另一個作者的倉庫名只差一個字母，AI 有引用錯倉庫的風險。

監測表把 X 帳號、GitHub 帳號和代表性開源專案都檢測到了，個人定位幾乎沒有偏差；修正建議也確實指出了沒做到的地方——看完就立刻去補上了。

> 分數不是重點。真正有價值的是：**每個扣分點能回到一個公開頁面，每個建議能落到一個具體欄位，過一兩週還能用同一組問題複測。**

## 拿自己的 IP 跑時，照這張清單檢查

1. 先寫公開事實基準卡，不把隱私和動態數字混進去；
2. 固定助手、日期、語言和 5—10 個問題；
3. 每個問題獨立檢索，不讓 AI 只照抄基準；
4. 實體出現、身份準確、來源可靠分開打分；
5. 本人主頁或專案優先，第三方轉載只做輔助證據；
6. 把"沒出現、說錯、認錯人、來源太弱"分開；
7. 建議落到頁面、欄位和複測方法；
8. 不自動改主頁、不自動發布，不承諾左右模型答案；
9. 保留結果，下次用同一口徑複測才看得出變化。

以前做個人 IP 總盯著知名度，現在還要多問一句：**當別人讓 AI 介紹我時，出來的資訊夠不夠準確？**把問題固定下來、把證據鏈補齊、把不穩定的數字剔出去，一次模糊的"搜搜看"就變成一套可重複執行的公開資料體檢。
