# 分類太細反而難找：541 個 GPT 提示詞案例重新歸類

> 場景：收集 GPT-Image2 提示詞案例時總覺得越多越好，攢到 541 個問題也來了——案例散在 GitHub 倉庫、README 和本機資料夾，分類越分越細，想找一條「國風水墨海報」得在幾個類之間來回翻。

> 前置條件：豆包與飛書帳號一致；專案資料已上傳飛書雲端硬碟或知識庫（可 @ 引用文件、雲端檔案、聯絡人和歷史對話）。

原來的管理方式：案例全堆在 README 和 gallery 文件裡手動分了 13 類；風格標籤 19 個、場景標籤 10 個，三套維度互相交叉；本機檔案和 GitHub 版本經常對不上。**這套分類是按時間順序搭的，從沒站在檢索者的視角設計過——分類維度越疊越多，最後反而變成查找的最大障礙。**

## 第一步：一句話讓豆包開始幹活

資料收攏進飛書後，全程不用寫複雜提示詞：

```text
幫我分析這個專案的案例分類體系 @awesome-gpt-image-2 專案資料
先看看現有分類有什麼問題，再根據真實搜尋詞重新設計
```

它會自動讀案例資料、統計分類分布、找出同義詞和交叉項。

## 第二步：量化診斷現有分類的五個硬傷

1. **同義詞標籤滿天飛**：19 個風格標籤裡 `Character` 用了 113 次、`Characters` 只用 2 次——完全是同一個東西；`Product`/`Products`、`Infographic`/`Charts`、`Realistic`/`Photography` 全是重複，19 個標籤其實 12 個就夠；
2. **同一概念出現在三個維度**：「海報」在 category 和 styles 裡都有，「歷史」在三層都出現——用戶不知道從哪個入口找；
3. **垃圾桶分類**：`Other Use Cases` 塞了 28 個案例，什麼都有，等於沒分類；
4. **薄分類撐不起一級目錄**：4 個一級分類合計才佔 11% 的案例；
5. **內部術語用戶看不懂**：`R&D`、`Prompt as Code` 這類詞，一般用戶搜尋時根本不會用。

更關鍵的一步：它從 541 個案例的真實標題裡提取高頻搜尋詞，**反向推導用戶的真實檢索習慣**——搜「海報/封面/宣傳」82 次、「資訊圖/技術圖解」48 次、「介面/截圖/App」38 次、「人像/肖像/頭像」28 次、「插畫/國風/水墨」25 次。用戶打開提示詞庫時帶著明確的落地目標：「我要做一張 XX 圖」。**分類體系圍繞產出物來搭，分類名直接對應用戶要完成的最終目標**——這是整個重構的核心支點。

## 第三步：從真實搜尋詞出發重新設計

新分類 **13 個 → 8 個，全部按產出物命名**，合計 541 個一個不多不少、沒有垃圾桶。合併邏輯：

- **介面與資訊圖**：UI、Dashboard、資訊圖、技術圖解在用戶心智裡都是「結構化資訊」，合在一起 140 個是最大類；
- **插畫與藝術**：國風/古風/水墨/歷史題材本質是插畫藝術風格，併入後「國風」透過別名直接命中；
- **場景·空間·敘事**：建築、城市、故事板、世界場景都是「大空間/世界觀」類產出物；
- **角色與人物**：專指虛擬角色/卡牌/3D 角色，真實人像歸「攝影與寫實」；
- **Other Use Cases 拆散**：28 個案例逐條歸入對應分類。

分類精簡了，但搜尋不能丟：給每個分類配**別名表**——搜「國風/古風/水墨」→ 插畫與藝術，搜「人像/肖像/頭像」→ 攝影與寫實，搜「Logo/VI/標誌」→ 品牌與標誌，搜「詳情頁/包裝/主圖」→ 商品與電商視覺。

## 第四步：批量遷移到飛書知識庫

在知識庫按 8 個新分類建一級目錄，然後：

```text
按照新分類映射表，把 cases.json 裡的 541 個案例重新打 category 標籤
然後按 8 個分類批量建立飛書文件，放到對應的知識庫目錄下
舊的分類錨點保留跳轉，不要刪
```

它會批量改寫 category 欄位、呼叫飛書介面批量建文件歸入目錄、舊 URL 錨點保留跳轉（收藏的舊連結不失效）、案例 id 和圖片路徑不變（GitHub 連結不斷）。**不要一次性全量改**：分階段來——先改標籤（低風險）→ 再改分類（中風險）→ 最後改前端展示和文件，每一步都能回滾。

## 第五步：用真實查詢測試

| 真實查詢 | 舊結構 | 新結構 |
| --- | --- | --- |
| 國風水墨海報 | 在 History 和 Illustration 之間猶豫 | 直接插畫與藝術，一步命中 |
| 寫實人像 | Photography 和 Characters 之間猶豫 | 攝影與寫實，別名「人像」直達 |
| App 介面截圖 | UI 分類內混有 Poster 內容形成干擾 | 直接進入介面與資訊圖 |
| 角色卡牌 | 3D 卡牌散在 Illustration 裡 | 角色與人物，命中更集中 |
| 城市建築地圖 | Architecture 和 Scenes 間來回猶豫 | 場景·空間·敘事 |

10 條測試查詢裡，5 條完全消除了多分類間反覆跳轉的猶豫，4 條命中路徑更短，1 條語義匹配精度明顯提升。後續迭代接入了 GA4 真實搜尋日誌，基於真實用戶行為再校準一次別名映射表——只需微調別名規則，不用推翻已驗證的分類架構。

## 分階段遷移清單

| 階段 | 做什麼 | 風險 |
| --- | --- | --- |
| 0 | 匯出真實搜尋詞，校準別名表 | 唯讀 |
| 1 | 合併同義標籤（Characters→Character 等） | 低 |
| 2 | 按映射表批量改寫 category 欄位 | 中 |
| 3 | 更新前端展示、搜尋別名、舊 URL 跳轉 | 中 |
| 4 | 更新文件的分類標題和錨點 | 低 |
| 5 | 用真實查詢跑回歸，對比零結果查詢是否下降 | 驗證 |

最大的感受：**知識庫管理以前是體力活，現在變成了動動嘴的事**——豆包負責讀資料、跑統計、找問題、設計方案、批量遷移，人只在關鍵節點做判斷和確認。老專案沉澱的經驗不用一直閒置，用 AI 搭配飛書知識庫把它盤活，落地過程比想像中順利很多。
