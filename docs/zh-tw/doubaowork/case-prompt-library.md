# 541 個提示詞案例越分越亂？按產出物重新歸類，飛書裡一搜就中

你攢 GPT 提示詞案例時，總覺得越多越好——直到某天想找一條「國風水墨海報」，在 History 和 Illustration 之間來回翻，才發現分類越細反而越難找。你案例散在 GitHub 倉庫、README 和本地資料夾，維度疊了一層又一層，最後分類本身成了查詢的最大障礙。這篇拿 541 個真實案例做一次重新歸類，核心就一句：分類名直接對應使用者要完成的最終目標。

> 前置條件：豆包與飛書賬號一致；專案資料已上傳飛書雲盤或知識庫（可 @ 引用檔案、雲盤檔案、聯絡人和歷史對話）。

## 第一步：一句話讓豆包開始幹活

你資料收攏進飛書後，全程不用寫複雜提示詞，直接把專案丟給它：

```text
幫我分析這個專案的案例分類體系 @awesome-gpt-image-2 專案資料
先看看現有分類有什麼問題，再根據真實搜尋詞重新設計
```

你提交後，它會自動讀案例資料、統計分類分佈、找出同義詞和交叉項。

## 第二步：量化診斷現有分類的五個硬傷

你讓豆包先算出「病」在哪，而不是憑感覺改。實測揪出五處：

1. **同義詞標籤滿天飛**：你看到 19 個風格標籤裡 `Character` 用了 113 次、`Characters` 只用 2 次——完全同一個東西；`Product`/`Products`、`Infographic`/`Charts`、`Realistic`/`Photography` 全是重複，19 個標籤其實 12 個就夠；
2. **同一概念出現在三個維度**：你看到「海報」在 category 和 styles 裡都有，「歷史」在三層都出現——你不知道從哪個入口找；
3. **垃圾桶分類**：你 `Other Use Cases` 塞了 28 個案例，啥都有，等於沒分類；
4. **薄分類撐不起一級目錄**：你 4 個一級分類合計才佔 11% 的案例；
5. **內部術語使用者看不懂**：你 `R&D`、`Prompt as Code` 這類詞，普通使用者搜尋時根本不會用。

你更關鍵的一步，是讓它從 541 個案例的真實標題裡提取高頻搜尋詞，反向推導使用者的真實檢索習慣——搜「海報 / 封面 / 宣傳」82 次、「資訊圖 / 技術圖解」48 次、「介面 / 截圖 / App」38 次、「人像 / 肖像 / 頭像」28 次、「插畫 / 國風 / 水墨」25 次。你開啟提示詞庫時帶著明確的落地目標：「我要做一張 XX 圖」。分類體系圍繞產出物來搭，分類名直接對應使用者要完成的最終目標——這是整個重構的核心支點。

## 第三步：從真實搜尋詞出發重新設計

你新分類 13 個 → 8 個，全部按產出物命名，合計 541 個一個不多不少、沒有垃圾桶。合併邏輯：

- 介面與資訊圖：你 UI、Dashboard、資訊圖、技術圖解在使用者心智裡都是「結構化資訊」，合在一起 140 個是最大類；
- 插畫與藝術：你國風 / 古風 / 水墨 / 歷史題材本質是插畫藝術風格，併入後「國風」通過別名直接命中；
- 場景·空間·敘事：你建築、城市、故事板、世界場景都是「大空間 / 世界觀」類產出物；
- 角色與人物：你專指虛擬角色 / 卡牌 / 3D 角色，真實人像歸「攝影與寫實」；
- Other Use Cases 拆散：你 28 個案例逐條歸入對應分類。

你分類精簡了，但搜尋不能丟：給每個分類配別名錶——搜「國風 / 古風 / 水墨」→ 插畫與藝術，搜「人像 / 肖像 / 頭像」→ 攝影與寫實，搜「Logo / VI / 標誌」→ 品牌與標誌，搜「詳情頁 / 包裝 / 主圖」→ 商品與電商視覺。

## 第四步：批次遷移到飛書知識庫

你先在知識庫按 8 個新分類建一級目錄，然後讓豆包批次改寫標籤並建檔案：

```text
按照新分類對映表，把 cases.json 裡的 541 個案例重新打 category 標籤
然後按 8 個分類批次建立飛書檔案，放到對應的知識庫目錄下
舊的分類錨點保留跳轉，不要刪
```

它批次改寫 category 欄位、呼叫飛書介面批次建檔案歸入目錄、舊 URL 錨點保留跳轉（收藏的舊連結不失效）、案例 id 和圖片路徑不變（GitHub 連結不斷）。你不要一次性全量改：分階段來——先改標籤（低風險）→ 再改分類（中風險）→ 最後改前端展示和檔案，每一步都能回滾。

## 第五步：用真實查詢測試

你用 10 條真實查詢回測，確認分類真能落地：

| 真實查詢 | 舊結構 | 新結構 |
| --- | --- | --- |
| 國風水墨海報 | 在 History 和 Illustration 之間猶豫 | 直接插畫與藝術，一步命中 |
| 寫實人像 | Photography 和 Characters 之間猶豫 | 攝影與寫實，別名「人像」直達 |
| App 介面截圖 | UI 分類內混有 Poster 內容形成幹擾 | 直接進入介面與資訊圖 |
| 角色卡牌 | 3D 卡牌散在 Illustration 裡 | 角色與人物，命中更集中 |
| 城市建築地圖 | Architecture 和 Scenes 間來回猶豫 | 場景·空間·敘事 |

你回測的 10 條測試查詢裡，5 條完全消除了多分類間反覆跳轉的猶豫，4 條命中路徑更短，1 條語義匹配精度明顯提升。你後續迭代接入了 GA4 真實搜尋日誌，基於真實使用者行為再校準一次別名對映表——只需微調別名規則，不用推翻已驗證的分類架構。

## 常見問題

**分類越細越方便找嗎？**
你反過來想：越細越容易把同一個概念塞進三個維度。案例散在 GitHub、README 和本地，維度疊多了，分類本身就成了查詢障礙。先按產出物命名，比按內部術語分更準。

**重構要一次全改完嗎？**
你別一次性全量改。先合併同義標籤（低風險），再改分類欄位（中風險），最後動前端和檔案，每一步留回滾空間。

**舊連結和圖片會失效嗎？**
不會。你讓豆包保留舊分類錨點跳轉、案例 id 和圖片路徑不變，GitHub 連結不斷，收藏的舊地址照樣能開啟。

**怎麼知道新分類真能命中？**
你拿 10 條真實查詢回測：5 條消除多分類猶豫、4 條路徑更短就說明有效。再接 GA4 搜尋日誌微調別名，不用推翻架構。

**別名錶有什麼用？**
你使用者的搜尋詞和分類名常常對不上（「人像 / 肖像 / 頭像」指向同一類）。別名把同義說法都引到正確分類，搜哪個都能直達。
