# 自動化邊界：讓系統可停、可接管、可恢復

## 白話導讀

這一章幫你給「自動化」裝上一個能隨時停下的剎車。你一旦讓系統定時跑週報、自動發群訊息，最怕的不是它不幹活，而是出錯後還在繼續發、原件被改、沒人接手。你團隊若沒這套剎車，一次欄位變化就可能讓日報連錯一整週；本章給你一張自動化執行卡：停機、人工接管、回退、撤銷、恢復五個動作分別管什麼，你讀完就能在上線前把「誰在異常時接手、原件怎麼保住、出錯怎麼撤回」寫清楚。你以後部署自動化，心裡有底、出事不慌。

## 30 秒結論

<span id="claim-automation-human-handoff-01" data-claim-id="claim-automation-human-handoff-01"></span>本書主張：自動化只有在異常時能夠停止執行、保護原件、通知責任人、轉為人工完成並經重新驗證後恢復，才具備進入企業執行的基本條件。

白話解釋：這條為什麼這麼定？你部署自動化前最該想清楚的是「它出事時誰接手」。如果一個定時任務跑偏了還在發舊口徑結論，損失會比人工慢一點大得多；所以你能不能停、能不能接管、能不能恢復原樣，才是它該不該上線的門檻，你要把這三件事當成上線閘門去卡。

- 自動校驗、人工複核、交付驗收和動作確認是四個不同控制點。
- 停用、人工接管、回退、撤銷和恢復處理不同狀態，不能混用。
- 寫入、傳送、釋出等高風險動作必須服從治理等級和明確授權。

## 你可能遇到的場景

你想讓系統每週自動整理週報或會議紀要：讀取本週檔案、生成摘要、列出行動項，再發到群裡。輸入例子是「週五 17:00 前的會議紀要、上週週報和已確認的群聊物件」。你先別急著開定時器，先把停機、人工接管、回退和恢復寫進任務；你別等第一次出錯才補這些開關——那時原件可能已經改了、訊息已經發了。

## 你會拿到什麼

你上線前先把這張卡備齊，它最少包含四塊，缺一塊上線就別放行：

1. 觸發條件、輸入版本和空資料處理；
2. 自動校驗、人審、交付驗收、動作確認四個控制點；
3. 停用開關、接管人、備用流程、通知內容和影響範圍；
4. 上一穩定版本、重驗樣本、撤銷方式和恢復批准記錄。

## 照著做

1. 先用週報或會議紀要跑一次草稿流程，明確哪些步驟只讀、哪些步驟會寫入、傳送或釋出。
2. 為日期、行數、總額、重複執行和權限變化設定機器檢查，並安排內容複核者與動作責任人。
3. **中間檢查點：**故意用缺檔案、欄位變化或物件不明的輸入演練停機；確認系統保留原件、隔離草稿並通知接管人。
4. 用正常、邊界、失敗樣本重驗，業務負責人批准影響處理後，才恢復自動排程。

## 案例參考

可先看[優克拉：產品研發與考勤算薪](/zh-tw/qwenwork/case-youkela)，把其中的資料核對和高後果人工確認當作執行邊界練習；案例陳述不等於你的自動化效果或可無人值守承諾。你拿它當練習素材即可，別把案例裡的順暢當成你自己的驗收結論。

## 做完檢查

執行一次故障演練：讓輸入版本不匹配，確認新任務停止、原件未改、責任人收到通知、當前產物標為草稿，並能按備用流程完成交付；否則不得上線。

白話解釋：你別跳過這次演練。讓輸入版本故意對不上，看系統是不是真的停下、真的沒動原件、真的通知到人；任一項不滿足，它就不能上線，你後面省下的時間會在出事時加倍賠回去。

## 需要注意

發生校驗失敗、重複執行、權限變化或物件不明時，立即停用並停止外發，保留原件、現場和日誌，人工接管當前任務；若新版本失敗，回到上一穩定版本，修復後經業務負責人重新確認再恢復。

白話解釋：你遇到這幾類訊號時，第一反應就是「先停、別發、留現場」。原件和日誌留住了，後面才有得查、有得退；你別想著先湊合發出去再補，那樣往往越錯越大。

## 為什麼重要

自動化擴大了單次錯誤的影響範圍。欄位變化可能讓日報連續出錯，登入失效可能造成靜默缺數，重複排程可能多次傳送，介面變化可能讓電腦操控點錯物件。只准備一個「關閉開關」不能解決已經執行的動作，也不能說明由誰完成剩餘任務。

你作為企業 AI 負責人需要把故障處理設計成正常執行的一部分。業務負責人則需要知道，異常出現後原件是否安全、交付是否延期、誰正在接管，以及何時允許重新上線。

白話解釋：這節是給管理者看的。你作為業務負責人，真正要問的不是「它能不能跑」，而是「它跑歪了誰頂上、原件還在不在、什麼時候能放心恢復」。你把這三點問住了，自動化才算可控。

## 方法或模型

四個控制點分別回答不同問題：

| 控制點 | 固定定義 | 典型證據 | 責任角色 |
|---|---|---|---|
| 自動校驗 | 檢查機器可判定的格式、範圍、完整性和一致性條件 | schema 結果、行數、雜湊、勾稽和重複檢查 | 工作流 Owner |
| 人工複核 | 判斷事實、語義、專業質量和風險是否正確 | 抽查記錄、修改清單、專業意見 | 內容複核者或專業 Owner |
| 交付驗收 | 決定產物是否滿足任務卡並可進入下一環節 | 通過、退回或有條件通過記錄 | 業務負責人 |
| 動作確認 | 授權實際傳送、寫入、釋出、刪除或其他外部動作 | 確認人、物件、範圍、時間和變更清單 | 動作責任人 |

白話解釋：這四個點你別混。機器能判的格式、範圍歸「自動校驗」；事實對不對歸「人工複核」；能不能進下一環節歸「交付驗收」；真要發出去、寫進去歸「動作確認」。你把一個點當另一個點用，責任就糊了。

五個執行術語也不能互相替代：

| 術語 | 含義 | 適用時點 |
|---|---|---|
| 停用 | 阻止新的自動執行開始 | 發現系統性風險或需要維護時 |
| 人工接管 | 由責任人接手當前未完成任務 | 當前交付仍需按時完成時 |
| 回退 | 切換到上一穩定版本、規則或人工流程 | 新版本失敗且尚可使用既有路徑時 |
| 撤銷 | 在系統支援且風險可控時反向處理已完成動作 | 錯誤寫入、傳送或釋出已經發生後 |
| 恢復 | 修復、重驗和批准後重新開放自動執行 | 根因已處理且恢復條件滿足時 |

白話解釋：停用、接管、回退、撤銷、恢復五件事不是一回事。你停了不等於撤回了已發的訊息，回退了不等於撤銷了錯誤寫入；所以每張執行卡要把五者各自什麼時候用、誰批准寫明白，別用一個詞含糊帶過。

最小接管與恢復鏈固定為：

1. **觸發條件**：自動校驗失敗、輸入異常、權限變化、重複執行或人工報告事件。
2. **停止執行**：阻止新任務和剩餘高風險動作，不繼續嘗試未知步驟。
3. **保護原件**：保留輸入、現場、日誌和未修改的原檔案，隔離錯誤產物。
4. **通知責任人**：說明影響範圍、當前狀態、截止時間和需要的決定。
5. **人工完成**：由指定接管人按備用流程完成必要交付，並記錄人工變更。
6. **定位失敗**：區分輸入、權限、工具、規則、模型和環境原因。
7. **修正版本**：建立新版本，不覆蓋失敗版本和證據。
8. **重新驗證**：用正常、邊界和失敗樣本重跑自動校驗及人工複核。
9. **批准恢復**：業務負責人確認影響已處理，工作流 Owner 再開放排程。

G2/G3 動作的具體確認規則以第 11 章為唯一規範來源；本章只要求自動化能夠呼叫相應確認和接管機制。

官方幫助中心分別說明桌面端定時任務、電腦操控和 IM 頻道等能力。 [R5](/zh-tw/qwenwork/appendix-sources#r5) [R6](/zh-tw/qwenwork/appendix-sources#r6) [R7](/zh-tw/qwenwork/appendix-sources#r7) 能力入口和可用範圍可能變化，應在當前賬號、系統版本和組織授權下實測。

以週一經營日報為例：排程開始前檢查輸入目錄和日期；生成後自動勾稽總額；內容複核者檢查異常解釋；業務負責人驗收；傳送群訊息前由動作責任人確認。你若遇到欄位變化導致勾稽失敗，要確認系統真的停在草稿狀態、保留原表並通知接管人，不得繼續傳送舊口徑結論。

## 企業行動

為一個已有自動化補齊執行卡：

| 必填項 | 最小內容 |
|---|---|
| 觸發與輸入 | 排程規則、輸入位置、日期範圍、空資料處理 |
| 四個控制點 | 各自條件、責任人、證據和超時處理 |
| 故障處置 | 停用開關、接管人、備用流程、影響通知 |
| 版本恢復 | 上一穩定版本、重驗樣本、恢復批准人 |
| 已執行動作 | 是否可撤銷、撤銷責任人、不能撤銷時的補救方式 |

白話解釋：你給已有自動化補這張卡時，最難填的往往是「已執行動作能不能撤銷」。你儘早想清楚：發出去的訊息撤不回怎麼辦、寫進去的資料怎麼補，比上線後再手忙腳亂強得多。

你看到這些訊號立刻停用並接管：機器校驗失敗卻仍準備外發；輸入範圍或賬號權限突然變化；相同任務重複執行；原件可能被覆蓋；當前動作無法確認物件和影響；沒有可聯絡的責任人或備用流程。

## 邊界與下一步

並非所有任務都適合定時或無人值守。你判斷來源不穩、驗收靠專業判斷、失敗不可逆或影響外部物件的任務，應保留人在迴路中；低風險讀取和草稿生成也仍需失敗提醒與執行記錄。

你判斷一個任務該不該無人值守，就看來源穩不穩、驗收靠不靠專業判斷、失敗可不可逆、會不會影響外部物件。本章定義執行控制，不定義組織治理等級；治理章節將統一說明資料敏感度、人機責任和高風險動作門檻。

## 術語翻成人話

| 術語 | 人話 |
|---|---|
| 自動化執行卡 | 你給一個定時任務寫的「說明書+安全繩」，寫清誰接手、怎麼停、怎麼退 |
| 自動校驗 | 機器能判的格式、範圍、勾稽檢查，它只管「對不對得上」，不管「對不對」 |
| 動作確認 | 真要發出去、寫進去、刪掉前的那次授權，是最高風險的一道閘 |
| 停用 | 攔住新的自動執行，等於先喊停，但已經發出的動作還在 |
| 回退 | 切回上一個能用的版本或人工流程，不等於撤回已發生的錯誤 |
| 撤銷 | 在系統支援時反向處理已完成的寫入、傳送或釋出，往往有條件且有時限 |
| 恢復 | 根因修好、重驗通過、負責人批准後，才重新放開自動排程 |

## 常見問題

**你該怎麼判斷一個自動化任務能不能上線？**
你先做一次故障演練：故意讓輸入版本不匹配，看它是不是真的停下、原件是不是沒動、責任人是不是收到通知、草稿是不是能按備用流程交付。四項全滿足才上線，任一項不滿足都先別放。

**你部署自動化時，最容易漏掉哪一道控制點？**
最容易漏的是「動作確認」。你常把傳送、寫入當成流程自然結果，忘了它是最該明確授權的高風險動作；誰確認、確認什麼物件、什麼範圍、什麼時間，都要寫進執行卡。

**跑歪了但訊息已經發出去了，你該怎麼辦？**
你先停用、留現場和日誌，再走「人工接管→回退→撤銷」。注意回退不等於撤銷：已發的訊息要單獨撤回，已寫的資料要單獨補正，能撤就撤，不能撤就說明補救方式。

**你作為業務負責人，這一章要你留什麼證據？**
至少三樣：接管人和備用流程是誰、上一穩定版本在哪、恢復由誰批准。沒有這些，異常發生時你只能臨時抓人，交付延期還說不清責任。

**哪些任務你不該做成無人值守自動化？**
來源不穩、驗收靠專業判斷、失敗不可逆或會影響外部物件的任務，你都該把人留在迴路裡；哪怕是低風險讀取，也得有失敗提醒和執行記錄，不能靜默跑。
