# 案例：公眾號文章→飛書知識庫全自動流水線

> 改編自 TRAE 官方論壇使用者 HancksLiu（產品經理）的實戰帖[《我用 TraeWork 打造「公眾號文章→飛書知識庫」全自動流水線》](https://forum.trae.cn/t/topic/172002)（2026-07）。配套技能已開源：[yucai0302/wechat-to-feishu-kb](https://github.com/yucai0302/wechat-to-feishu-kb)。

## 三個痛點

1. **微信生態封閉**：通用爬蟲抓公眾號返回空殼頁面或提示"需在微信客戶端開啟"，AI 搜尋引擎無法穿透微信 CDN 防護，"一鍵收藏"類工具對公眾號基本無效；
2. **閱讀與沉澱割裂**：文章收藏了就再也沒開啟過，無法納入個人或團隊知識庫檢索複用；
3. **手動整理太貴**：一篇 5000 字文章手動歸檔 15-20 分鐘，每週 10-15 篇，光歸檔就要 3-4 小時。

## 方案架構：兩個 Skill + 雙模式

```text
Skill 1  wechat-article-saver     抓取公眾號文章 → 存本地 Markdown
Skill 2  wechat-to-feishu-kb      本地 Markdown → 飛書知識庫
─────────────────────────────────────────────
即時模式：聊天中直接發文章連結 → Skill 自動觸發抓取 + 寫入
批次模式：連結逐行貼進 pending.txt → 每晚 22:00 定時任務自動處理
```

### 抓取：四層降級策略

微信公眾號的反爬是核心難點，Skill 內建了四層降級，任一層成功即繼續：

1. Playwright + Chromium 無頭瀏覽器渲染；
2. HTTP fetch 帶反爬 Header（User-Agent、Accept-Language 等）;
3. TraeWork 內建 WebFetch 工具；
4. 手動貼上原文兜底。

正文用 Mozilla Readability 提取、Turndown 轉 Markdown，單篇約 30 秒。

### 沉澱：飛書對接

飛書側只用了 lark-cli 的兩個能力：`wiki + node-create`（建知識庫節點）和 `docs + update`（寫入檔案內容）。本地同時保留 Markdown 雙備份，可被 Obsidian / Notion / Logseq 直接索引。

## 效果

| 指標 | 之前 | 之後 |
| --- | --- | --- |
| 單篇整理 | 15-20 分鐘 | 5 秒（即時）/ 0 秒（定時） |
| 每週節省 | — | 3-4 小時 |
| 每月節省 | — | 約 15 小時 |
| 知識可檢索 | 收藏夾裡吃灰 | 100%（飛書 AI 問答 + 本地全文搜尋） |
| 團隊複用 | 無 | 知識庫全員可訪問 |

## 最重要的一課：定時任務的提示詞

作者第一次配定時任務時只寫了一句"抓取文章存知識庫"，**失敗**——缺少 space_id、認證方式、檔案路徑等引數。修正後的認知：

> **定時任務本質上是一個「無人值守的對話」，提示詞越詳細，越穩定。**

把完整執行步驟、引數、錯誤處理邏輯全部寫進任務說明後一次跑通。詳見[自動化定時任務](/zh-tw/traework/07-automated-tasks)的寫作清單。

## 遷移到你的場景

這條流水線的骨架是通用的：

```text
資訊源（連結/郵件/報表）→ 抓取 Skill（多層降級）→ 標準化中間格式
→ 沉澱 Skill（飛書/Notion/本地知識庫）→ 定時排程 + 即時對話雙模式
```

可替換的資訊源：行業資訊頁、競品 changelog、應用商店評論、團隊週報郵件。作者也坦承現狀的侷限——本地 pending.txt 的收集方式"還不夠智慧"，理想的自動推薦受限於微信生態的封閉性。

## 安全提醒

- 抓取流程涉及登入憑證時，勿在公共裝置操作；
- 尊重內容版權：歸檔自用與二次分發是兩回事，團隊知識庫注意授權邊界。
