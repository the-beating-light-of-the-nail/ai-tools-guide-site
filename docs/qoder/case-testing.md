# 案例：单元测试从 0 到 70

> 测试是所有人都同意重要、大多数人都拖着不写的东西。本章案例：一个 4 万行的 Node.js 服务，测试覆盖率 3%，用 Quest Mode 在两周内拉到 71%，且没有出现「为覆盖率而写」的垃圾测试。重点不在数字，在流程——这套流程可以直接复制到你的项目。

## 场景与痛点

- 仓库：内部订单服务，4.2 万行 TypeScript，86 个模块；
- 现状：只有工具函数有零星测试，覆盖率 3%；每次发版靠「祈祷 + 灰度」；
- 人的尝试：团队两次立誓补测试，都在两周后放弃——手写测试太枯燥，写一个用例要读十分钟代码。

这正是「机械 + 可验收」的典型场景：适合交给 Agent 批量生产，人来定标准。

## 第一步：先定「什么是好测试」

直接说「把覆盖率提上去」会得到灾难：Agent 会写出 500 个断言强度为零的快照测试，覆盖率数字漂亮，回归一个都拦不住。所以先写 Spec，核心是**四条验收标准**：

```yaml
# specs/testing.yaml
objective: 为核心模块补齐单元测试
acceptance:
  - 每个测试必须至少包含一个具体断言（禁止空跑、禁止仅 smoke）
  - 每个用例名能读出「场景 + 预期」：如 计算折扣_会员且满减叠加_取更优价
  - 边界用例覆盖：空输入、非法输入、并发/超时（如有）
  - 新增测试全部通过，且跑完不超过 60 秒
constraints:
  - 不修改业务代码；发现疑似 bug 一律报告而不是顺手改
  - mock 只 mock 外部依赖（网络、时间、随机数），不 mock 被测函数内部
```

最后一条 constraint 是关键：**发现 bug 不许顺手修**。测试和修复混在一次任务里，出了问题说不清是哪边引入的——分两个任务做。

## 第二步：批量执行——按模块切片

4 万行不可能一个 Quest 吃完（上下文撑不住，一次产出也无法 review）。切片策略：**按模块切，每个模块一个 Quest，Spec 完全复用**。

用 Worktree 并行跑 4 个模块（见[并行任务与 Worktree](/qoder/adv-worktree)），每个 Quest 的提示词只有一行差异：

```text
为 src/modules/pricing 及其依赖编写单元测试，遵循 specs/testing.yaml 的全部验收标准。
先列出你计划覆盖的函数清单和用例设计，我确认后再写代码。
```

「先列清单再动手」这个步骤省了一次大返工：第一个切片里，Agent 的清单包含了 3 个已经废弃的函数（死代码），人在计划阶段就砍掉了，避免产出 30 个无意义用例。

## 第三步：人做什么——抽查与守门

Agent 产出的 380 个用例，人不可能逐个读。守门方法分三层：

1. **自动门槛**：CI 强制覆盖率不低于上一版（只升不降），测试时长超时直接红；
2. **抽样 review**：每个模块人读 5 个用例，重点看断言强度和 mock 边界。发现「快照测试混进来」就整批退回该模块；
3. **变异抽查**（进阶）：随机改坏 3 处业务逻辑，跑测试——如果测试全绿，说明用例是摆设，退回重写。

第三层最有杀伤力：**能被「故意改坏」拦住的测试才是真测试**。

## 第四步：顺手收下副产品

过程中 Agent 报告了 11 个「疑似 bug」（constraint 生效，没顺手修）。整理成清单：

```text
# bug 清单（来自测试任务，全部待人工确认）
P1  pricing/promotion.ts:42  满减与折扣叠加时可能双计优惠
P2  order/state.ts:110       状态机缺少「已取消→退款中」的迁移校验
P3  ...（略）
```

这 11 个报告是本次任务真实价值的一半——**写测试的过程等价于一次深度代码审计**。把确认过的 bug 交给独立的修复 Quest（每个 bug 一份 Spec，含「修复后新增回归测试」的验收）。

## 数字与复盘

| 指标 | 之前 | 两周后 |
| --- | --- | --- |
| 覆盖率 | 3% | 71% |
| 用例数 | 21 | 401 |
| 测试时长 | — | 48 秒 |
| 人投入 | — | 约 6 小时（抽查+守门+bug 确认） |
| 发现疑似 bug | — | 11 个（6 个确认修复） |

复盘三条经验：

1. **先定质量标准再批量生产**，否则会大规模生产垃圾；
2. **切片复用 Spec**，让第二片之后的人力投入趋近于零；
3. **测试任务要「只测不改」**，副产品 bug 单独走修复流程。

## 任务清单

如果你想在自己的仓库复现这个案例：

- [ ] 写一份测试 Spec（四条验收 + 不改业务代码的约束）
- [ ] 选 1 个核心模块跑第一个切片，先看用例清单再放行
- [ ] 抽查 5 个用例：断言强度、mock 边界、命名可读性
- [ ] 做 3 处「故意改坏」变异测试，验证用例有效性
- [ ] CI 加覆盖率门槛，锁定战果
