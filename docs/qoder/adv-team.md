# 团队落地：规范、权限与验收

个人用好 Qoder 靠手感，团队用好 Qoder 靠系统。只有三个问题需要回答：

1. **一致性**：不同人委派的任务，产出为什么风格统一？
2. **安全性**：智能体的权限边界在哪，谁负责看住它？
3. **可交接**：一次成功的任务，怎么变成所有人都复用的资产？

## 一致性：把规范沉进仓库

团队统一从三层载体获得一致性，全部进版本管理：

```text
.qoder/
├── rules/project.md      # 编码规范、命名、测试要求
├── quest/                # Spec 模板与历史（评审对齐材料）
└── repowiki/             # 全员共享的项目认知
```

**Spec 模板化**是性价比最高的一步。给团队定一个标准结构：

```text
# 任务：{标题}
## 需求描述
## 设计方案（技术选型 / 模块划分 / 数据流）
## 任务拆解
## 验收标准（可判定、逐条可勾选）
## 边界与不做的事
```

从此任何成员委派的 Quest，Spec 都是同一种形状，评审效率翻倍。

## 安全性：权限分级 + 红线清单

Qoder 自带分级权限与工具白名单，团队要在此之上补一份**红线清单**，写进规则：

```yaml
rules:
  - name: 凭证红线
    description: 任何密钥、生产凭证不得进入对话与文件变更
  - name: 生产环境
    description: 不得对生产数据库执行任何写操作；只读账号仅限只读查询
  - name: 依赖变更
    description: 升级/新增依赖必须在 Spec 中显式声明理由
  - name: 迁移脚本
    description: 涉及数据迁移的命令一律人工批准，禁止自动执行
```

权限开放的原则：**从每步确认起步，按「命令类别」逐类放开，永远不按「人」放开**。白名单里只放无副作用命令（lint、test、build）。

## 可交接：Case 沉淀机制

每个团队都应该有自己的案例库。一次任务值得沉淀的标准：

- 过程中有真实的问题与解决（不是一次就成）；
- 做法可复用（换了数据还能跑）；
- 有明确的验收标准。

沉淀的最小结构：

```text
1. 场景与问题：谁、在什么任务里、遇到什么困难
2. 使用的 Skill / 配置：来源、安装、必要配置
3. 任务描述：原始提示词、Spec、步骤
4. 执行过程：关键操作、权限要求、安全边界
5. 实际效果：结果证明（截图 / 数据）
6. 验收标准：怎么判断完成
```

放在团队 Wiki 或独立仓库均可，关键是**让新人能按图索骥地重放**。

## 度量：怎么知道落地有效

别看「用了多少积分」，看三个指标：

1. **Spec 一次通过率**：评审时不需要大改的比例——衡量需求书写质量；
2. **验收一次通过率**：Run 之后 Accept 不需要返工的比例——衡量委派与执行质量；
3. **Case 复用次数**：案例库被别人重放的次数——衡量沉淀质量。

## 试点路径（两周方案）

```text
第 1 周
  周一  选 1 个真实模块 + 2 名成员试点
  周二  写 .qoder/rules + Spec 模板
  周三  各自跑 1 个 Quest，每步确认模式
  周五  复盘：返工点、红线、规则补充

第 2 周
  周一  生成全量 Repo Wiki，团队共享
  周二  并行 2 个任务，尝试 Worktree
  周四  第一次放开白名单命令自动执行
  周五  沉淀 3 个 Case，定团队验收标准 v1
```
