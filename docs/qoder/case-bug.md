# 案例：啃下其他工具卡住的 Bug

## 场景与问题

一个基准测试的 Bug 修复，先后换过多个主流 AI 编程工具都卡住了——这类「多个工具都搞不定」的问题，往往是**跨文件、长链路、需要真实运行验证**的疑难杂症。Qoder 处理这类问题的优势来自它的执行闭环：读 → 改 → 跑 → 依据真实结果自我修正。

## 为什么有些 Bug 会卡住别的工具

| 常见卡点 | 传统工具的表现 | Qoder 的解法 |
| --- | --- | --- |
| 复现链路长 | 单轮问答里给猜测 | 自主执行：真的跑起来复现 |
| 跨文件传导 | 只改看得见的文件 | 仓库级上下文 + Wiki 引用 |
| 结果依赖运行时 | 无法验证 | 跑测试、看输出、自我修正 |
| 线索在数据里 | 不读数据 | 读日志/数据文件取证 |

## 操作过程

**第 1 步：写一份「Bug 档案」再发任务。** 好的 Bug 委派必须包含可复现信息：

```text
修复一个基准测试不稳定的问题：

现象：
- tests/test_benchmark.py::test_latency 偶发失败，概率约 10%
- 失败信息：assert p99 < 200ms，实测 210~240ms

复现：
- pytest tests/test_benchmark.py -k test_latency --repeat 20

已知线索：
- 只在 CI 的 Linux 容器里出现，本地 macOS 无法复现
- 疑似与 GC 或容器 CPU 限流有关，未证实

要求：
- 先定位根因，写清证据链，再修复
- 修复不能让基准测试失真（禁止 sleep 掩盖问题）
- 修复后 --repeat 50 全绿
```

**第 2 步：让 Quest 先做诊断，不许直接改。** Spec 驱动的好处在这里体现：Spec 里要求「先定位根因、写证据链」，就把「瞎改一通碰运气」挡在了执行之前。

**第 3 步：监控执行中的自我修正。** Action Flow 里会看到智能体跑测试 → 看输出 → 排除假设 → 再跑的循环。这正是 read-edit-verify-iterate 闭环的价值：**每一轮修正都基于真实结果而不是想象**。

**第 4 步：验收看证据，不看声明。** 任务报告说修好了不够，自己再跑：

```bash
pytest tests/test_benchmark.py -k test_latency --repeat 50
```

## 验收标准

- [ ] Spec 或报告中有明确根因与证据链（不是「可能是」）
- [ ] 修复不含掩盖性代码（sleep、跳过、放宽断言）
- [ ] 复现命令在修复后全绿
- [ ] 相关边界测试被补充

## 复盘要点

- **Bug 委派的核心是给复现方式**。能复现，智能体就能迭代；不能复现，再强的工具也只能猜；
- 修复后把根因写进规则或 Wiki 对应模块页，同类问题下次直接有据可查；
- 一次跑不定就分两段：先开一个「只诊断不改码」的 Quest，拿到根因再开修复任务。
