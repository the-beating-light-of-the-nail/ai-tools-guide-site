# 并行任务与 Worktree

## 从串行到并行的思维转变

一个人的旧姿势是「一次做一件事」。有了 Quest，正确姿势变成：**早上派出去一批，白天管进度，晚上验收**。注意力是稀缺资源，并行是把它用在刀刃上的方法。

## Local 并行 vs Worktree 并行

| | Local 并行 | Worktree 并行 |
| --- | --- | --- |
| 工作区 | 共用主工作区 | 每个任务独立隐藏工作区 |
| 主分支 | 会被直接修改 | 始终干净 |
| 适合 | 互不冲突的轻任务 | 中等复杂、要反复 Apply 的任务 |
| 迭代 | 受当前文件状态影响 | 无限次 Apply |

**选择规则：两个任务可能碰同一个文件 → 必须一个走 Worktree。** 否则就会出现两个智能体在同一个工作区互相踩脚的事故。

## 一天的时间线示例

```text
09:30  开 3 个 Quest（全部 Worktree）：
       A. 用户反馈的列表页分页 Bug（Spec 驱动）
       B. 给支付模块补集成测试（Spec 驱动）
       C. 官网文案页新板块（搭建网站场景）
09:45  各自确认 Spec，Run
10:30  C 转为 Ready，Preview 验收，追加一轮样式调整
11:00  A 卡在 Action Required：智能体请求执行一条迁移命令
       审查命令 → 批准 → 继续跑
14:00  B 完成，跑全量测试验收，Accept 变更
16:00  A 完成，审查 diff，Accept
17:30  本地跑一次整体回归，全部合入
```

要点：**人在三个任务间的角色是调度员和验收员，全程没有写过一行代码。**

## 侧边任务：不打断主线的支线

复杂任务执行中出现衍生问题（「顺手把这个警告也修了？」），不要让它挤进主线。用侧边任务处理：

- 主任务的上下文和 Spec 保持纯净，不被支线污染；
- 支线完成后独立验收，再决定要不要合入。

新版本 Qoder 还提供 Plan（执行前梳理需求方案）与 Goal（围绕目标持续执行并验证）等面向长程任务的功能，与侧边任务配合使用。

## 并行的管理纪律

任务一多，混乱的成本就上来了。三条纪律：

1. **命名即文档**：任务标题写清「模块 + 动作 + 场景」，别叫 test1、test2；
2. **一个任务一个分支**：合入顺序 = 风险从低到高；
3. **验收不过就重来，不要缝缝补补**：Quest 的无限次 Apply 是给你重试的，不是给你容忍半成品的。

## 风险与止损

- **积分消耗**：并行任务同时烧 Credits，跑之前看余额，长任务分配好档位（重要任务 Ultimate，杂活 Efficient）；
- **冲突管理**：两个任务产出冲突时，先合验收标准更严的那个；
- **及时止损**：一个任务反复 Error 超过三轮，停下来人肉看一眼——通常是需求本身有问题，不是智能体的问题。
