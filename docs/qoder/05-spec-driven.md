# Spec 驱动开发：把需求写成验收标准

Quest 的 Spec 驱动场景，是 Qoder 与「补全式工具」拉开差距的地方。完整流程只有四步：**需求澄清 → 生成 Spec → 审查修改 → 执行验证**。

## 第一步：需求澄清

输入任务后，Quest 可能以多选题形式提出澄清问题。三种处理方式：

- 让 Quest 自动选择默认答案；
- 手动选择后继续；
- 直接跳过进入对话。

**建议第一次认真答**。澄清问题暴露的往往是需求里的真空地带，这些真空地带最后都会变成返工。

## 第二步：生成 Spec

Quest 会审查项目记忆与上下文、分析代码库结构，生成一份结构化 Spec 文档，通常包含：

- **需求描述**：目标与边界
- **设计方案**：技术选型、模块划分、数据流（复杂任务还会生成 Mermaid 流程图）
- **任务拆解**：分步执行计划
- **验收标准**：怎样算完成

Spec 自动保存在项目的 `.qoder/quest/` 目录，支持流式输出与下载。

## 第三步：审查 Spec——最重要的一步

**Spec 方向错了，后面全错。** 点击 Run 之前，逐条核对：

1. 设计方案是否与你理解的一致？
2. 验收标准是否可执行、可判定？
3. 有没有范围蔓延（做了你没要求的事）？
4. 有没有遗漏（错误处理、边界条件、测试）？

不满意就直接在对话里说：`「验收标准里加上：密码错误返回 401；去掉单点登录，本期不做」`。

## 一个高质量需求模板

Spec 的质量直接由需求描述决定。对比：

❌ 模糊需求：`帮我做个登录功能`

✅ 高质量需求：

```text
实现用户登录功能：
- 后端：Spring Boot 3.4 + Spring Security 6.x
- 认证方式：JWT Token，有效期 2 小时
- 密码加密：BCrypt
- 接口路径：POST /api/v1/auth/login
- 请求体：{ "username": "string", "password": "string" }
- 响应体：Result<LoginVO>，LoginVO 包含 token 和 userInfo
- 异常处理：用户不存在返回 404，密码错误返回 401
- 需要单元测试：正常登录、用户不存在、密码错误三个场景
- 代码风格：遵循项目 .qoder/rules/project.md 中的规范
```

写清楚**技术约束、接口契约、异常路径和测试要求**，Spec 的产出质量会成倍提升。

## 第四步：执行与验证

点击右上角 **Run / 立即开始** 后：

1. Action Flow 视图实时显示执行计划、进行中的操作与阻塞问题；
2. To-do List 随执行推进逐项勾选；
3. Changed Files Tab 查看变更，可逐文件 Accept / Discard；
4. 完成后生成**任务报告**，总结变更内容、测试结果与验证结果。

执行中追加需求完全合法：`「再加一个刷新 token 的接口」`，Quest 会调整计划继续。

## 决定执行环境

- 简单直接的任务选 **Local**，主工作区直接改；
- 中等复杂、想保住当前分支干净状态的，选 **Worktree**（可无限次 Apply 迭代，详见[并行任务与 Worktree](/qoder/adv-worktree)）。

## Spec 文档的复用价值

`.qoder/quest/` 里的 Spec 不是用完即弃：

- 团队评审时，Spec 就是对齐文档；
- 出问题回溯时，Spec 是「当时说好要做什么」的凭据；
- 换个人接手时，Spec 加任务报告就是交接材料。

建议把 Spec 纳入版本管理（见[团队落地](/qoder/adv-team)）。
