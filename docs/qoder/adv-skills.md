# 打造自己的 Skills 与插件

## 什么时候该做 Skill

判断标准很简单：**同一个提示词，你写过第三遍**。这时候它已经不是对话，是资产。Qoder 生态提供 20000+ 技能与 70+ 专家套件，但最有价值的永远是你从自己工作流里提炼的那几个。

适合做成 Skill 的三类东西：

1. **流程型**：周报生成、发布检查清单、新模块脚手架；
2. **规范型**：代码风格套件、测试要求、目录结构约定；
3. **资产型**：把项目的领域知识（术语表、业务规则）打包成智能体可引用的资料。

## Skill 的结构

一个 Skill 本质是「说明书 + 可选脚本」，让智能体按既定打法处理一类任务：

```text
my-weekly-report/
├── SKILL.md        # 说明书：什么时候触发、步骤、输出格式
└── scripts/        # 可选：辅助脚本
    └── aggregate.py
```

SKILL.md 的写法要点：

- **触发条件写具体**：「当用户要求生成周报/数据汇总时」；
- **步骤可判定**：「第一步核对文件数量是否为 7，不足先提问」；
- **输出给样例**：贴一段期望产物的样子，胜过一百句形容词；
- **声明边界**：明确不做什么（「不修改原始 CSV」）。

## 从案例到 Skill 的提炼流程

以周报为例：

```text
第 1 周  对话里现写提示词 → 产物返工两次 → 终于满意
第 2 周  复制上周提示词，改路径 → 一次通过
第 3 周  把提示词整理成 SKILL.md，固化判断标准（±20% 标黄）
第 4 周  团队同事装上同一个 Skill，产出格式一致
```

提炼时机：**在第 2 周和第 3 周之间**——做法已经稳定，但还没开始腐烂。

## 插件与专家套件

Qoder 的 70+ 专家套件覆盖常见领域（前端、数据分析、文档处理等），原则：

- 先搜生态，**有现成的就别自造**，自造的维护成本是你的；
- 现成的不满足时，优先 fork 改造而不是从零写；
- 团队自用的 Skill 独立建仓管理，和业务代码分开。

## Skill 的质量清单

- [ ] 触发条件明确，不会误伤其他任务
- [ ] 步骤有失败分支（文件缺失、格式异常时怎么办）
- [ ] 输出有样例
- [ ] 声明了安全边界（不动什么、不读什么）
- [ ] 换一个人用，不需要你口头解释
